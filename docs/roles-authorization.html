Role Authorization

Who each role can see and manage, and how the account (company) scope applies. Hierarchy: SUPER_ADMIN > COMPANY_ADMIN > ADMIN > SALES / SUPPORT / USER. HR_MANAGER is standalone (not in the hierarchy).

Account & data scope

Role Account Data scope Users table Account selector Manage users
SUPER_ADMIN None Platform-wide (all companies) All users Visible · all Yes
ADMIN None Global 1 All users Visible · all Yes
COMPANY_ADMIN admin of one company Required Own company only Own company only Visible · locked 2 Yes
HR_MANAGER time / attendance only Required Company-wide time/attendance Read-only (pickers) 3 Hidden No
SALES Required Own account No access Hidden No
SUPPORT Required Own account No access Hidden No
USER Required Own account No access Hidden No
Yes allowed / global Required / scoped account-bound None / No not allowed

Notes

  • 1 ADMIN is global on the account axis (no account). Server-side data scoping still keys off workspace (WorkspaceContext.isAdmin() = ROLE_ADMIN && workspaceId == null), so an ADMIN that belongs to a workspace is workspace-scoped there — the account and workspace axes are not yet unified.
  • 2 COMPANY_ADMIN sees the header account dropdown, but the Users endpoint overrides any chosen account with the caller's own — they cannot list another company's users regardless of selection.
  • 3 HR_MANAGER may GET /users so attendance pickers can list people, but cannot create, update, delete, or toggle users. Its user listing is not yet company-scoped.
  • Account assignment is enforced on admin CRUD (/users). Invitation and self-registration paths still create users without an account.
  • Account filtering for non-Users entities (Contacts, Opportunities, …) is applied via a request parameter the client sends; it is not yet derived server-side for non-admins, so it is a UI scope, not a hard boundary.
